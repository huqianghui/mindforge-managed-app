> 证据分三级，每条结论都标明属于哪一级：

## 二、managed app 托管在哪里

### 2.1 静态文件〔实测〕

| 观察 | 值 |
|---|---|
| 应用域名 | `apps-9ae71e53dd544a3690ac0815fd93f03c.pp.us-il301.gateway.prod.island.powerplatformusercontent.com` |
| 网关集群 | 响应头 `x-ms-gateway-clusters: prdil301wus`，宿主配置 `clusterName: prdil301wus`、`clusterCategory: firstrelease` |
| 区域 | 响应头 `x-ms-request-id: unitedstatesfirstrelease.westus2:...`，即美国 West US 2 的 first release 环 |
| 内容 | `/` 返回我们 `dist/index.html`，`/assets/*`、`/content/*` 就是 `npm run build` 的产物 |

每个应用一个**独立子域名**（`apps-<appId>`），浏览器的同源策略天然把不同应用隔开：应用 A 的脚本读不到应用 B 的 localStorage 和 cookie。

注意域名是 `powerplatform**usercontent**.com`，不是 `powerplatform.com`。这是常见的安全做法：用户代码放在单独的"用户内容"域名下，即使应用里有恶意脚本，也碰不到平台主域名的 cookie。

### 2.2 应用被允许做什么：CSP〔实测〕

#### 先说 CSP 是什么

CSP 全称 **Content Security Policy**（内容安全策略），是浏览器的一项安全机制：**服务器返回网页时附带一张白名单，告诉浏览器这个页面只能从哪里加载脚本、图片、iframe，只能向哪里发请求。** 页面上的代码想越界，浏览器直接拦下。

- **在哪里**：HTTP 响应头 `content-security-policy`，和网页一起从服务器发来。
- **怎么读**：`指令 来源`。`'self'` = 只允许本域名，`'none'` = 完全禁止。例如 `connect-src 'self'` 表示 `fetch` / XHR / WebSocket 只能连本域名。
- **违反了会怎样**：浏览器拒绝执行，并在开发者工具 Console 报错，例如 `Refused to connect ... because it violates the Content Security Policy directive: connect-src 'self'`。代码本身没错，只是被拒绝。
- **为什么管用**：规则由**服务器**下发，页面代码改不了（最多再加一条更严的 meta 标签，不能放宽）；执行者是**浏览器**，不依赖应用代码守规矩。
- **原本防什么**：最初用来防 XSS（跨站脚本攻击）——即使攻击者把恶意脚本注入页面，CSP 也能阻止它运行或把数据发出去。Managed Runtime 把它用得更进一步：**不只防攻击者，也约束应用本身**。
- **自己看**：打开应用 → F12 → Network → 选中应用的 HTML 文档请求 → Response Headers 里的 `content-security-policy`。

常见指令：

| 指令 | 管什么 |
|---|---|
| `default-src` | 其他指令没写时的默认值 |
| `script-src` | 能执行哪里的 JavaScript |
| `style-src` | 能用哪里的 CSS；`'unsafe-inline'` 表示允许内联样式 |
| `connect-src` | `fetch`、XHR、WebSocket、EventSource 能连哪里 |
| `frame-src` / `child-src` | 能嵌入哪里的 iframe |
| `worker-src` | 能否启动 Web Worker / Service Worker |
| `img-src`、`font-src`、`media-src` | 图片、字体、音视频从哪里加载 |
| `form-action` | 表单能提交到哪里 |
| `frame-ancestors` | **谁能把我嵌进去**（方向与 `frame-src` 相反） |

#### 本应用的 CSP

应用的 `index.html` 返回的 Content-Security-Policy（原文）：

```text
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
connect-src 'self';                 ← fetch / XHR / WebSocket 只能回自己的域名
frame-src 'self'; child-src 'none'; ← 不能嵌入任何外部 iframe
worker-src 'none';                  ← 不能起 Web Worker
img-src 'self' data:; media-src 'self' data:; font-src 'self';
form-action 'none'; manifest-src 'none'; base-uri 'self';
frame-ancestors 'self' https://*.powerapps.com
                https://play.managedapps.cloud.microsoft
                https://play.preview.managedapps.cloud.microsoft
```

这几行决定了 managed app 的能力边界：

| 想做的事 | 能否 | 原因 |
|---|---|---|
| `fetch('https://api.openai.com/...')` 或任何外部 API | ❌ | `connect-src 'self'` |
| 嵌入 Copilot Studio 的网页聊天 iframe | ❌ | `frame-src 'self'` |
| 从 CDN 加载脚本、字体、图片 | ❌ | 全部 `'self'`，依赖必须打包进来（我们的 `three`、`react-force-graph` 都打包在 bundle 里，所以没问题） |
| Web Worker（例如在后台线程跑向量检索） | ❌ | `worker-src 'none'` |
| 被嵌到别的网站里 | ❌ | `frame-ancestors` 只允许宿主 |
| 调 Connector | ✅ | 不由应用直接发请求，而是交给宿主，见第四节 |

**这就是"为什么网页嵌入在 managed app 里不能用"的直接答案**：宿主给应用设置的 CSP 禁止嵌入任何外部 iframe。另外两个原因（嵌入代码要求 agent 关闭认证、应用读不到 iframe 里的回答）也成立，但 CSP 这一条已经足够把这条路堵死。

> 顺带：CSP 是**响应头**，由平台网关下发，应用改不了。`vite.config.ts` 里加 meta 标签也只能让它更严，不能放宽。

### 2.3 宿主给应用开放了哪些能力：JSON-RPC 方法表〔实测〕

宿主加载器（`/_platform/app/loader`）是一个公开的静态页面，里面列出了应用可以请求的全部方法。按用途分组：

| 组 | 方法 | 说明 |
|---|---|---|
| 应用 | `app/getContext` | 即 SDK 的 `getContext()` |
| 身份 | `auth/getUser`、`auth/getGatewayToken`（`acquireToken` 是它的旧别名）、`auth/signOut` | `getUser()` 走这里。`getGatewayToken` 只签发访问**应用文件网关**的 PoP token（绑定调用方的公钥），不是 Graph 或 Connector 的 token，见 2.5 |
| 授权 | `challenge/consent` | 首次使用某 Connector 时弹出同意 / 建连接 |
| 数据 | `data/getAppConnections`、`data/ensureConnectionsReady`、`data/connectionStateChanged` | 解析 `connectionReferences` |
| HTTP | `http/send`、`http/result` | **Connector 调用的唯一出口** |
| 中间层函数 | `function/invoke`、`function/result`、`function/cancel` | 尚未开放，见 2.4 |
| Cowork | `cowork/invokePrompt`、`cowork/streamPrompt`（流式）、`cowork/cancel`、`cowork/listTasks`、`cowork/getTaskArtifacts`、`cowork/downloadFile`、`cowork/downloadAllFiles` | **实验性**，见第五节 |
| 遥测 | `telemetry/trackEvent`、`telemetry/subscribeMetrics` | SDK 的 logger |
| 生命周期 / 开发 | `channel/*`、`runtime/*`、`loader/*`、`dev/*` | 加载、`ms app dev` 热更新等 |

`http/send` 有两条硬校验（类型定义里标注为 "Load-bearing for security"）：

1. 请求里的 `apiId` 必须在应用已解析的连接里；
2. 请求 URL 的 origin 必须等于**该连接**的 `runtimeUrl`。

两条都通过，宿主才替你注入连接的认证信息并转发。宿主允许的目标只有两类：`*.environment.api.powerplatform.com`（Power Platform API）和 API Hub（Connector 运行时）。

也就是说：**应用能访问的外部世界，就是 `ms.config.json` 里登记过的那些 Connector，一个都不多。** 这就是 managed app 的治理模型落在代码上的样子。

### 2.4 还没开放的"中间层"〔实测 + 第三方〕

`function/*` 方法和对应的类型已经在协议里了：

- 调用参数里带 `tenantId / userObjectId / environmentId / appId / commitHash / timeout`；
- 终止原因包括 `invocation_timeout`、`memory_limit_exceeded`、**`isolate_crashed`**；
- 函数内的 `fetch()` 走 `http/send` 的 `appFetch` 策略：只允许平台自己的命名空间，其他目标一律 403，不注入任何凭据。

`isolate_crashed` 这个词说明函数很可能跑在 **V8 isolate** 里（和 Cloudflare Workers 同类的轻量隔离），而不是容器。第三方文章（recursion.no）也写到"中间层（应用内的服务端逻辑）不在 public preview 范围内"。所以：**现在 managed app 没有后端；协议显示后端会以"受限的函数"形式出现，而且同样不能随意访问外网。**

### 2.5 宿主用 iframe 装应用，却不让应用再嵌 iframe：矛盾吗？〔实测〕

不矛盾。两者方向相反，目的相同——**宿主掌控所有边界，应用只待在中间那一层**：

```text
宿主（play.managedapps.cloud.microsoft）   ← 登录、token、头部、治理都在这一层
  └─ iframe：应用（apps-<id>.powerplatformusercontent.com）
        └─ iframe：外部网站   ← 被 CSP frame-src 'self' 禁止
```

| 方向 | 谁定的规则 | 目的 |
|---|---|---|
| 宿主嵌入应用（向内） | 宿主 | 把应用**关进**一个隔离的格子 |
| 应用嵌入外部（向外） | 宿主通过 CSP 下发给应用 | 不让应用**开后门**通到外面 |

#### 宿主为什么用 iframe 装应用

"在外层加认证和用户信息"是原因之一，但更根本的是**隔离**。实测到的五层保护：

1. **认证在外层，token 不给应用。** 登录（MSAL）发生在宿主页面。应用拿到的身份只有 `getUser()` 的三个字段（姓名、objectId、tenantId）。调 Connector 时应用只把请求交给宿主（`http/send`），宿主校验后注入凭据。`auth/getGatewayToken` 按类型定义只签发访问应用文件网关的 PoP token，资源固定、绑定调用方密钥。
2. **应用文件本身也在认证后面。** 不登录直接访问：

   ```text
   /                        → 401
   /content/manifest.json   → 401
   /_platform/app/loader    → 200（加载器是公开的空壳）
   ```

   加载器拿到 token 后才取应用文件。**这是和 GitHub Pages 的本质区别**：文章不是"知道网址就能看"。
3. **不同域名，浏览器自动隔离。** 应用在独立的 `powerplatformusercontent.com` 子域名，按同源策略读不到宿主页面的 DOM、cookie、token；每个应用一个子域名，应用之间也互相读不到。
4. **iframe 的 `sandbox` 属性限制行为。** 宿主给应用 iframe 设置了：

   ```text
   allow-forms allow-popups allow-popups-to-escape-sandbox allow-pointer-lock
   allow-scripts allow-same-origin allow-modals allow-downloads
   allow-top-navigation-to-custom-protocols allow-storage-access-by-user-activation
   ```

   注意**没有** `allow-top-navigation`：应用不能把整个浏览器页面导走，无法伪造登录页钓鱼。`allow` 属性只给本应用域名开放 geolocation、microphone、camera、fullscreen、clipboard-write。
5. **`frame-ancestors` 防止应用被别处嵌入。** 只有宿主域名能嵌应用，用户看到应用时外面一定套着宿主。

#### 为什么不让应用再嵌外部 iframe（以及不让直接 fetch）

| 风险 | 说明 |
|---|---|
| 数据外流 | 应用可把页面上的业务数据塞进 iframe 的 URL 参数或用 postMessage 发给外部网站，完全绕过 Connector、DLP 和管理员审核 |
| 钓鱼 | 外部页面出现在"公司认证过的应用"里，用户会误以为可信 |
| 治理失效 | 管理员在后台看到"只用了 SharePoint 连接器"，实际却在和任意网站通信 |

`connect-src 'self'` 的道理相同：**应用能接触的外部世界，必须全部经过 Connector 这道登记过的闸口。**

#### 会不会放开

技术上可以（CSP 支持按白名单放开域名）。先例：据第三方周报，Power Apps Code Apps 有可配置的 frame-src，微软确认嵌入 PDF 需放开 `blob:`。managed app 目前未找到类似设置〔待实测〕；即使开放，大概率也是**管理员在租户级加白名单**，而不是应用作者自己决定。

## 三、harness 托管在哪里

### 3.1 能确定的部分

| harness | 运行在哪里 | 证据 |
|---|---|---|
| Standard | Copilot Studio **经典运行时**（前身 Power Virtual Agents），属于 agent 所在的 Power Platform 环境。Connector 调用路径是 `/powervirtualagents/dataverse-backed/authenticated/bots/{agent}/proactivecopilot/executeAsyncV2` | 〔官方〕GitHub 讨论中微软答复确认 |
| GitHub Copilot | Copilot Studio **Agentic Runtime**，内部代号 `mcs-dracarys`。Connector 的 swagger 里只有一个内部的"续接对话"路径 `/copilotstudio/agenticruntime/.../conversations/{id}/continue`；返回是 `text/event-stream` 流 | 〔官方〕同上答复确认"runs on a different runtime"；路径与代号来自提问者对 swagger 的分析，〔第三方〕自定义连接器文章确认流式 |
| Copilot Chat | 不在 Copilot Studio 运行时里执行。Copilot Studio 只编写配置（指令、知识、动作），执行者是 **Microsoft 365 Copilot 自己的编排器** | 〔官方〕"extend Microsoft Copilot Chat" |

agent 定义本身存在环境的 Dataverse 里（路径中的 `dataverse-backed`）。所以**Standard 和 GitHub Copilot 两种 agent 的"数据"在同一个地方，"执行"在两套不同的服务里**。

### 3.2 GitHub Copilot harness 的沙箱：能查到什么，查不到什么

官方说法〔官方〕：

- "runs each task in a secure sandbox governed by Copilot Studio"；
- 比较文档："A **Bash container** provides access to tools and libraries that aren't available in the standard harness"，并有**容器内的文件系统**，用来读写大文件和生成文档；
- 它和 GitHub Copilot "shares underlying technology and **SDK components**"，但数据不发往 GitHub Copilot 服务。

这句"共享 SDK 组件"是理解它的钥匙。GitHub Copilot SDK 是公开的〔官方，GitHub Docs / Build 2026〕，它把 GitHub Copilot 的 agent 循环做成可嵌入的运行时，部署方式有：

| 方式 | 说明 |
|---|---|
| 本地直接执行 | 工具调用直接在本机跑 |
| 每会话一个完整容器 | 一个 session 独占一个容器 |
| MXC 沙箱 | Microsoft eXecution Container：把声明式策略翻译成各 OS 的原生隔离（Windows ProcessContainer、macOS Seatbelt、Linux bubblewrap），控制文件、网络、进程访问；**不是 VM，也不是容器镜像** |
| 远程 / 云端 | GitHub 托管的临时 Linux 沙箱（`copilot --cloud`），按 CPU 秒、内存 GiB 秒计费 |

Copilot Studio 用的是哪一种、是否每个任务独占一个容器、容器多久回收、能否访问外网——**官方没有公开，我也没有找到可信的公开资料**。这是闭源的云服务，能拿到的只有文档、安全研究和网络抓包；GitHub Copilot harness 的执行发生在服务端，浏览器抓不到。所以这部分我只能说清"已知"和"未知"的边界，而不是猜一个答案。

一个**相邻但不同**的系统，有详细的第三方资料：BeyondTrust 对 Copilot Studio **code interpreter**（Standard harness 里"写 Python 并执行"的功能）的安全研究〔第三方〕：

- 内部代号：平台 Plex，code interpreter 子系统 MiddleEarth，属于 Power AI Operations 团队；
- 运行在 Azure 上的 **Windows Server 2022 容器**里：YARP 反向代理（:9001）→ 一个长期运行的 Python gRPC worker（:9002）；
- "沙箱"是同一个 Python 进程内的限制，**不是独立进程或 VM**；
- 环境变量 `CS_CLUSTERRING=mt`，研究者判断是**多租户共享**的预热容器池，实际停留约 30 分钟。

它告诉我们微软在这一代产品里实现"沙箱"的一种方式，但**不能直接套到 GitHub Copilot harness 的 Bash 容器上**：一个是 Windows + Python 进程内限制，一个明确是 Bash（Linux 系）容器。

## 四、它们怎么连接

### 4.1 managed app → Connector → Standard agent（我们第 5 阶段要走的路）

```text
③ 应用  MicrosoftCopilotStudioService.ExecuteCopilotAsyncV2(...)
   │  SDK: getClient().executeAsync → JSON-RPC http/send（带 apiId、connectionId）
   ▼
② / ① 宿主  校验 apiId ∈ 应用连接、URL origin == 连接 runtimeUrl
   │  用当前用户的 token 调 API Hub
   ▼
API Hub  /<connectionId>/powervirtualagents/.../proactivecopilot/executeAsyncV2
   │  以"用户自己的连接"身份（该连接不可共享）
   ▼
Copilot Studio 经典运行时（agent 所在环境）
   │  一次性返回 { lastResponse, responses[], conversationId }
   ▼
原路返回给应用
```

每一跳都是"请求—等待—一次性响应"，所以能通。

### 4.2 为什么 GitHub Copilot harness 接不上

| 卡在哪一跳 | 原因 |
|---|---|
| Connector 层 | `shared_microsoftcopilotstudio` 没有公开的"在 Agentic Runtime 上发起一轮"的操作〔官方确认〕 |
| 协议层 | Agentic Runtime 只回流式（SSE）；Power Platform Connector 不能把流交给调用方，单次请求约 120 秒超时〔第三方〕 |
| 应用层 | 应用不能绕过 Connector 直接连（`connect-src 'self'`）〔实测〕 |

三层全被堵住，所以不是"SDK 少一个函数"的问题。社区的自定义连接器只解决了第一层，第二层的限制（读完整个流再返回、超时丢失）依然存在。

### 4.3 宿主里已经有的另一条路：Cowork（实验性）

宿主已经实现了 `cowork/streamPrompt`：应用发一个 prompt，宿主替你连 Cowork 后端，把 SSE 流拆成 `started / text / status / tool / file / connectionRequired / done` 等事件**流式**推回应用。这正好绕开了 Connector 不能流式的限制。

但目前不可用于正式应用〔实测，类型定义原文〕：

- 标注 **"⚠️ Experimental — not part of the stable protocol"**，"Shapes may change or be removed without notice"；
- 默认关闭，需要宿主开发者设置里的 `cowork` 开关；
- 当前实现要求在开发者设置面板里**手工粘贴 `coworkToken`**；
- 公开的 SDK `@microsoft/managed-apps@0.6.0` 没有包装这些方法。

值得关注：**这很可能是将来 managed app 调用"带推理、带工具、流式输出"的 Copilot 的官方路径。**

## 五、回到参考应用

截图里的 CSU Investment Insights，Ask Copilot 底部写着 "Microsoft 365 Copilot, under your own sign-in"。结合以上：

- 它不可能用 iframe 嵌 Copilot（CSP 禁止）；
- 也不可能从浏览器直接调外部 API（CSP 禁止）；
- 所以只能是某个 Connector，或宿主的 `cowork/*` 通道。

候选：本租户可用的 `Work IQ Copilot MCP`（`shared_a365copilotchatmcp`，动作 `mcp_m365copilot`，SSO），或者 Copilot Studio Connector 调一个 Standard agent，或者 Cowork 通道。**具体是哪一个，要看它的网络请求才能确定**——这需要你同意我在浏览器里打开它（只看请求路径和 Connector 名称，不记录业务数据）。
