# 11 方案讨论

> 路线图 1–6 做完后的回顾：同一件事试过的几种做法、各自的代价，以及以后再做类似功能时怎么选。实测数据和踩坑过程在 [04](04-新功能开发指南.md)，这里只做比较和结论。基线 2026-10-28。

## 一、问答的三个后端

三个后端用**同一份本地检索结果和同一套提示词**（SOURCES + `[n]` + `RELATED:`），所以回答质量的差别主要来自模型和编排，而不是检索。

| | Work IQ（M365 Copilot） | Copilot Studio agent（Work IQ + agentId） | Azure OpenAI connector |
|---|---|---|---|
| 调用链 | 应用 → Work IQ Copilot MCP → Graph Copilot Chat API → M365 Copilot | 同左，M365 Copilot 再把这一轮交给 agent「Mindforge Ask」 | 应用 → Azure OpenAI connector → 自己的部署 |
| 身份 | 当前用户（SSO） | 当前用户（SSO） | 共享连接里的 API Key |
| 用户前提 | 每人要有 M365 Copilot 许可证 | 同左，且 agent 已发布到 Teams / M365 渠道 | 无；分享应用即可用 |
| 模型 | Copilot 自动路由，不能选 | 在 agent 里选（Standard harness） | 每次调用选部署（下拉框） |
| 上网 | 由 Copilot 决定 | agent 的 Web Search（Grounding with Bing），按指令只在资料没有答案时用 | 不能，只看 SOURCES |
| 同一问题耗时 | 15–26 秒 | 25–36 秒 | 4–8 秒 |
| 可观测 | 只有回答文本；回显 fileUris / autoExtractedFileUris | 同左 | 返回模型版本和 token 用量 |
| 计费 | 用户的 Copilot 许可证 | Copilot 许可证；agent 用到的 Copilot Studio 消息另计 | Azure 按 token |
| 改行为 | 只能改提示词 | 改 agent 指令、模型、知识、工具，需重新发布 | 改提示词或换部署，前端发版即生效 |

**怎么选**

- **默认用 Azure OpenAI**：快 3–5 倍，结果可复现，能看到用量。只要有自己的 Azure 资源，这是做应用内问答最直接的路。缺点是 key 由连接共享，配额和费用都算在资源所有者头上。
- **需要 agent 的能力时用 agent**：资料外查网页、调用工具、复用已经在 Teams / M365 里用的同一个 agent。代价是最慢，而且行为改动要在 Copilot Studio 里发布。
- **Work IQ 本体**适合"没有 Azure 资源、用户都有 Copilot 许可证"的组织，也是参考应用的做法。它的优势是零配置和企业 grounding，但不能选模型，速度也最慢档之一。

**为什么没有直接用 Copilot Studio Connector 调 agent**：`ExecuteCopilotAsyncV2` 要求 `notificationUrl` 回调，浏览器里的 managed app 收不到回调；未发布时又会重定向到门户，被 CORS 拦截。经 Work IQ 传 `agentId` 是目前唯一能从应用里同步拿到 agent 回答的路，见 [03 · 实测](03-Copilot-Studio集成指南.md#实测从-managed-app-调用-standard-agent2026-10-28)。

## 二、用户数据：App state 还是 Dataverse

| | App state（采用） | Dataverse 表 |
|---|---|---|
| 本租户结果 | 读写都通 | 读可以，写入动作被 DLP 屏蔽；SDK 的 `createRecordAsync` 走表格路径返回 404 |
| 隔离 | `x-ms-ownership: perUser`，平台强制 | 表的拥有者 + 安全角色 |
| 经过 Connector | 否（同源 `/.ms/state`） | 是，要授权连接，受 DLP 管控 |
| 本地调试 | 不行，只能部署后验证 | `ms app dev` 可用 |
| 共享给 agent / 流程 | 不能 | 能 |
| 成熟度 | 实验特性 | 正式功能 |

**结论**：只给本应用用的个人数据（进度、收藏、偏好）放 App state。要让 agent 或 Power Automate 读到同一份数据时才用 Dataverse，并且要先请管理员放开写入动作。不要手工把被屏蔽的动作补进 `dataSources.ts`，那等于绕过组织策略。

**最容易踩的坑**：App state 默认是**所有用户共享**的集合，必须手改 schema 加 `x-ms-ownership: perUser`。

## 三、Connector 接入检查清单

每接一个 Connector，按顺序过一遍，这些都是本项目实际踩到的：

1. `ms connector list --only-allowed` 看它在不在白名单；`ms app add data-source` 的输出里留意 **"Skipped N of M actions due to your organization's connector policy"**。被跳过的动作就是被 DLP 屏蔽了。
2. 生成的 service 返回类型可能是 `void` 或宽泛的 `any`（Work IQ 就是），实际返回格式要先在宿主里打印一次再写解析。
3. 连接参数不校验。Azure OpenAI 的资源名填成网址，连接仍显示 Connected，调用却一直 502。出问题先用 Power Apps API 读连接的非机密参数。
4. 共享连接（API Key 这类）部署时必须在 `ms.config.json` 声明 `allowedActions`，只放用到的动作。`ms app dev` 不查这一项，所以本地能跑不代表能部署。
5. 每个用户第一次调用时宿主会弹授权框，挂起的那次调用计时会包含等待授权的时间，不要拿它当性能数据。
6. 宿主外（`npm run dev`、GitHub Pages）SDK 调用不会返回也不会报错，必须有超时或"不在宿主"判断（`src/platform/user.ts`）。
7. `ms app deploy` 轮询超时不等于构建失败：先 `ms app build-status --commit <sha>`，成功后再 deploy 一次会直接用缓存的构建。

## 四、GitHub Pages 做不到的部分

GitHub Pages 版和本项目共享内容和大部分页面（导航、图谱、洞察、建议、统计、演进都是纯前端）。真正依赖平台的只有三类：

| 能力 | 依赖什么 | GitHub Pages 上的退路 |
|---|---|---|
| 识别用户 | 宿主的 `getUser()` | 无；只能匿名 |
| 按用户保存、跨设备同步 | App state | localStorage，只在本机 |
| 问答 | Connector（Work IQ / Azure OpenAI） | 只能演示检索；要真回答就得自己有后端和密钥，静态站放不了密钥 |

所以判断一个功能要不要放到 managed app，可以只问一句：**它需要知道"你是谁"，或者需要一把不能放进前端的凭据吗？** 都不需要的，纯前端实现，两个站点都能用。

## 五、还没定论的问题

- **Copilot Chat（声明式）agent 能否同样经 `agentId` 调用**：理论上它也发布在 M365 Copilot 里、有 titleId，〔待实测〕。如果能，就不需要 Standard harness 和 Copilot Studio 消息计费。
- **提示词里的网址是否拖慢 Work IQ**：`copilot_chat` 会把提示词里出现的网址取出来放进 `autoExtractedFileUris`，可能会去抓取。检索片段里常有原文链接，去掉之后耗时和回答会不会变，〔待实测〕。
- **多轮对话**：现在每次调用都是新会话，靠提示词里带最近 2 轮。Work IQ 返回了 `conversationId`，能否传回去续接，〔待实测〕。
